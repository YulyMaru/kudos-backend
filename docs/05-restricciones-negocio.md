# 05 · Restricciones de Negocio — UCO Kudos

Las restricciones de negocio son condiciones **no negociables** del entorno del proyecto que limitan las decisiones de diseño y planeación.

| Tipo | Restricción de negocio | Justificación | Plan de acción |
|------|------------------------|---------------|----------------|
| **Tiempo** | La solución debe estar entregada, desplegada y sustentada a más tardar el **viernes 13 de noviembre de 2026 a las 12:00 m.** | Fecha límite fijada por el curso Ingeniería del Software II. | Priorizar el flujo obligatorio (Publicar Kudo + notificaciones + auditoría) y el pipeline DevSecOps. Desplegar desde el primer día para eliminar riesgos de infraestructura. El resto de la plataforma se diseña y documenta. |
| **Humano** | El proyecto se desarrolla de forma **individual**: una sola persona cumple los roles de arquitecta, desarrolladora, tester y DevOps. | Modalidad definida por el curso. | Elegir un stack conocido (Java + Spring Boot, Angular), servicios gestionados y una arquitectura de Puertos y Adaptadores desplegada como una sola unidad para reducir la carga operativa. Automatizar pruebas y despliegue. |
| **Presupuesto** | Se cuenta con un presupuesto de **$0** para infraestructura y servicios. | Proyecto académico sin financiación. | Utilizar capas gratuitas: GitHub Actions, SonarCloud, Trivy, hosting y base de datos gestionada con plan gratuito, sandbox de WhatsApp y plan gratuito de correo transaccional. Documentar en los ADRs el camino de evolución a planes productivos. |
| **Legal** | Cumplir la **Ley 1581 de 2012 (Habeas Data)** y su reglamentación para el tratamiento de datos personales (correo, celular, nombre). | Legislación colombiana de protección de datos personales. | Minimizar los datos recolectados, cifrar el tráfico (HTTPS), restringir el acceso por rol, no exponer datos personales en logs y registrar el consentimiento de tratamiento en el registro. |
| **Legal** | Cumplir las políticas de uso de los proveedores de mensajería (WhatsApp Business / proveedor de correo), incluida la aceptación (*opt-in*) del destinatario. | Los proveedores exigen consentimiento del destinatario y plantillas aprobadas. | Usar el entorno sandbox/plantillas de prueba durante la línea base y documentar el proceso de aprobación de plantillas para producción. |
| **Institucional** | Los usuarios deben registrarse con **correo institucional** y **número celular**, y respetar la estructura organizacional (roles únicos, aprobaciones jerárquicas). | Reglas definidas por la UCO en el enunciado. | Modelar las reglas en la capa de dominio (entidades y servicios de dominio) para que no dependan de la interfaz ni de la base de datos. |
| **Proceso** | La sustentación es obligatoria e individual, y pueden solicitarse cambios de código, refactorizaciones e implementaciones en vivo. | Condición de evaluación del curso. | Mantener un código limpio, con capas claras y pruebas automatizadas que permitan hacer cambios con seguridad. Comprender cada decisión documentada en los ADRs. |
| **Proceso** | Toda la documentación debe entregarse en **Markdown (.md)**. | Formato documental exigido. | Documentación versionada en la carpeta `/docs` del repositorio, con diagramas en Mermaid/PlantUML. |
