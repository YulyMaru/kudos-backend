# 13 · Matriz Twelve-Factor App — UCO Kudos

| # | Factor | Qué exige | Cómo lo aplica UCO Kudos | Evaluación | Justificación |
|---|---|---|---|:-:|---|
| I | **Código base** | Un código base versionado, muchos despliegues. | Un repositorio por aplicación desplegable: `kudos-backend` y `kudos-frontend` en GitHub. Cada uno se despliega desde su rama `main`. | Cumple | Cada aplicación tiene un único repositorio, del que salen todos sus despliegues. |
| II | **Dependencias** | Declarar y aislar las dependencias explícitamente. | Back-end: `pom.xml` con versiones administradas por Spring Boot y Maven Wrapper (`mvnw`). Front-end: `package.json` y `package-lock.json`. La imagen Docker incluye todo lo necesario para ejecutarse. | Cumple | No se depende de nada instalado en el servidor; Trivy escanea las dependencias declaradas. |
| III | **Configuración** | Guardar la configuración en el entorno. | `application.properties` solo contiene marcadores (`${DB_URL}`, `${JWT_SECRETO}`…). Los valores reales están en variables de entorno; los secretos, en Secret Manager (producción) y GitHub Secrets (pipeline). | Cumple | Ninguna credencial está en el código; el mismo artefacto sirve para cualquier entorno. |
| IV | **Servicios de respaldo** | Tratar los servicios de respaldo como recursos conectables. | PostgreSQL, Supabase Storage, Brevo y Traccar SMS Gateway se conectan por URL y credenciales en la configuración, a través de adaptadores (puertos de salida). | Cumple | Cambiar de proveedor (por ejemplo, Brevo por Gmail o Meta por Twilio) es cambiar configuración o adaptador, sin tocar el negocio. |
| V | **Construir, publicar, ejecutar** | Separar estrictamente las etapas de construcción, publicación y ejecución. | **Construir:** GitHub Actions compila, prueba y genera la imagen Docker. **Publicar:** la imagen se etiqueta con el SHA del commit y se sube a Artifact Registry. **Ejecutar:** Cloud Run crea una revisión con esa imagen y la configuración del entorno. | Cumple | Cada versión desplegada es inmutable y se puede volver a una revisión anterior. |
| VI | **Procesos** | Ejecutar la aplicación como procesos sin estado. | Autenticación con JWT (sin sesiones en el servidor); archivos en almacenamiento de objetos; estado persistente en PostgreSQL. | Cumple Parcialmente | Excepciones conscientes: el broker WebSocket en memoria (sesiones de usuarios conectados) y la caché local de categorías. Por eso la línea base usa una sola instancia (ADR-004). |
| VII | **Asignación de puertos** | Exportar servicios mediante asignación de puertos. | El back-end es autocontenido (servidor embebido de Spring Boot) y escucha en `server.port=${PORT:8080}`, el puerto que asigna Cloud Run. | Cumple | No requiere un servidor de aplicaciones externo. |
| VIII | **Concurrencia** | Escalar mediante el modelo de procesos. | Escalado horizontal con instancias de Cloud Run; hilos virtuales para atender peticiones concurrentes; outbox con `FOR UPDATE SKIP LOCKED` apto para varias instancias. | Cumple Parcialmente | El diseño permite escalar horizontalmente, pero en la línea base `max-instances=1` por el broker WebSocket en memoria. |
| IX | **Desechabilidad** | Arranque rápido y apagado ordenado. | Apagado ordenado (`server.shutdown=graceful`); las notificaciones pendientes sobreviven en el outbox si el proceso se detiene; sondas de salud de inicio y disponibilidad. | Cumple Parcialmente | El arranque en frío de Spring Boot en Cloud Run puede tardar varios segundos (en AgroTrack se midieron 27 s); se mitiga con una instancia mínima durante la evaluación. |
| X | **Paridad entre desarrollo y producción** | Mantener desarrollo, pruebas y producción lo más parecidos posible. | La misma imagen Docker en todos los entornos; pruebas de integración con PostgreSQL real en contenedor (Testcontainers), el mismo motor de producción. | Cumple Parcialmente | Los proveedores de WhatsApp y correo funcionan en modo de prueba (número de prueba y plan gratuito), distinto de una operación productiva. |
| XI | **Logs** | Tratar los logs como flujos de eventos. | La aplicación escribe logs estructurados en JSON por la salida estándar; Cloud Run los envía a Cloud Logging. | Cumple | La aplicación no administra archivos de log ni su rotación. |
| XII | **Procesos de administración** | Ejecutar las tareas de administración como procesos puntuales. | Las migraciones de base de datos se ejecutan con Flyway, versionadas junto al código, al iniciar la aplicación. Los datos iniciales (categorías, usuarios de prueba) se cargan con migraciones. | Cumple | Las tareas administrativas usan el mismo código y configuración que la aplicación. |
